# Portal de Matrículas v2 (repositório VPS)

Este repositório é a evolução do Portal de Matrículas do Grupo Inter. Ele **não** está ligado ao Lovable, então nada daqui chega à produção sem uma decisão explícita.

Base: cópia do repositório `portal-de-matriculas` no commit `871cc07` (12/11/2026).

## Fases

| Fase | O que entrega | Situação |
|---|---|---|
| 0 | Tipo fixo de funil (LEADS / Pós-visita) e de etapa (agendada, reagendar, ganho) | Feita |
| 1 | Instâncias de WhatsApp pela Evolution API, QR Code, webhook e gravação das mensagens | Feita |
| 2 | Caixa de atendimento em tempo real, distribuição por atendente, mídia | Próxima |
| 3 | Conversa ligada ao card: criar oportunidade pela conversa, aba de conversa no card | — |
| 4 | Resumo da conversa com IA no card | — |
| 5 | Etiquetas, segmentação e disparo em massa com fila (serviço na VPS) | — |
| 6 | Retirada do Maxbot e API oficial da Meta | — |

## Como aplicar no banco (Supabase de testes primeiro)

Rode no SQL Editor, **nesta ordem**, antes de publicar o código. As duas migrações só acrescentam e podem ser rodadas de novo sem problema.

1. `supabase/v2/001_tipos_funil_etapa.sql`: cria `funnels.kind` e `funnel_stages.kind` e os preenche a partir dos nomes atuais. No fim do arquivo há uma consulta de conferência; rode-a e ajuste na tela **CRM › Funil** a etapa que ficou sem tipo.
2. `supabase/v2/002_whatsapp_base.sql`: cria as tabelas `whatsapp_instances`, `whatsapp_instance_secrets`, `wa_contacts`, `wa_conversations` e `wa_messages`.

> O código da Fase 0 lê a coluna `kind`. Se o código for publicado antes do SQL 001, as telas de funil e calendário dão erro.

## Variáveis de ambiente novas

| Variável | Exemplo | Para quê |
|---|---|---|
| `EVOLUTION_API_URL` | `https://evolution.seudominio.com.br` | Endereço da Evolution API |
| `EVOLUTION_API_KEY` | (chave global) | `AUTHENTICATION_API_KEY` configurada na Evolution |
| `PUBLIC_APP_URL` | `https://portal.seudominio.com.br` | Endereço público do portal, usado para montar a URL do webhook |

As variáveis que o portal já usa (`EXT_SUPABASE_URL`, `EXT_SUPABASE_PUBLISHABLE_KEY`, `EXT_SUPABASE_SERVICE_ROLE_KEY` etc.) continuam iguais. Veja o `.env.example`.

## Evolution API na VPS

- Use a **Evolution API v2** (Docker), com o PostgreSQL e o Redis próprios dela.
- Coloque-a atrás de HTTPS (Nginx/Traefik/Caddy) com um domínio próprio.
- Defina `AUTHENTICATION_API_KEY` com uma chave forte. É ela que vai em `EVOLUTION_API_KEY`.
- **Não** é preciso configurar webhook global: o portal configura o webhook de cada instância ao criá-la.

## Como funciona a Fase 1

- **Configurações › WhatsApp** (só para o administrador): criar a instância e escolher a unidade (ou todas), ler o QR Code, atualizar o status, testar o envio, reconfigurar o webhook, desconectar e excluir.
- Ao criar uma instância, o portal:
  1. gera um nome técnico único (`portal-<nome>-xxxxx`) e um segredo aleatório;
  2. cria a instância na Evolution com o webhook `PUBLIC_APP_URL/api/public/whatsapp-evolution`, mandando o segredo no cabeçalho `x-portal-webhook-secret` e no parâmetro `?s=`;
  3. guarda o token e o segredo em `whatsapp_instance_secrets`, uma tabela que o navegador não consegue ler.
- O webhook confere o segredo e grava: conexão, QR Code, mensagens recebidas e enviadas, e o status de entrega e leitura. Grupos, status e canais são ignorados. Mensagens repetidas não duplicam.
- Neste momento, só o administrador lê conversas e mensagens. A Fase 2 cria a caixa de atendimento e libera o acesso para os atendentes.

## Organização do código

```
src/lib/whatsapp/
  types.ts                 interface comum dos provedores (Evolution / Meta)
  evolution-events.ts      tradução dos webhooks da Evolution (pura, com testes)
  evolution.server.ts      chamadas HTTP à Evolution API v2
  provider.server.ts       escolha do provedor, URL do webhook, nomes e segredos
  ingest.server.ts         grava os eventos no banco
src/lib/ext/whatsapp.functions.ts      server functions da tela
src/routes/_authenticated/whatsapp.tsx tela Configurações › WhatsApp
src/routes/api/public/whatsapp-evolution.ts  webhook
```

## Checklist de teste (Supabase de testes + Evolution)

1. Rodar o SQL 001 e conferir os tipos das etapas em **CRM › Funil**.
2. Agendar uma visita num card de LEADS: o card vai para "Visita agendada".
3. No Calendário, marcar falta: o card vai para "Reagendar visita". Fazer o check-in: o card fica como ganho em "Visita realizada".
4. Repetir os passos 2 e 3 com matrícula num funil Pós-visita.
5. Rodar o SQL 002 e definir as três variáveis.
6. Criar uma instância, ler o QR Code e conferir que o status muda para "Conectado" sozinho.
7. Mandar uma mensagem para o número e conferir a linha nova em `wa_messages`, com o contato e a conversa criados.
8. Usar "Testar envio" e conferir que a mensagem chega e aparece em `wa_messages` como `out`.
